# 需求分析文档

> 项目：Mihomo 多网段精细分流配置  
> 版本：v8
> 最后更新：2026-10-02

---

## 1. 项目背景

用户拥有一台运行 OpenWrt 的路由器，已安装 Mihomo（原 Clash Meta）插件。需要实现一套**多网段、多机场、精细分流**的代理配置，满足全家多设备安全上网需求。

## 2. 用户画像

- 技术水平：熟悉路由器基础操作，了解代理概念，但非网络工程师
- 设备情况：多台手机/电脑/平板，通过不同 WiFi AP 接入
- 使用场景：AI 开发、海外社交、流媒体观看、设计工作、加密货币交易、游戏
- 核心诉求：**一次配置，全家受益，不同 WiFi 不同策略**

## 3. 功能需求

### 3.1 多网段隔离

| 需求编号 | 网段 | WiFi AP 名称 | 行为 | 优先级 |
|---------|------|-------------|------|--------|
| NET-01 | 192.168.31.x | ap-direct / br-lan | 全部直连，不经过任何代理 | P0 |
| NET-02 | 192.168.32.x | ap-rule | 按规则精细分流 | P0 |
| NET-03 | 192.168.33.x | ap-Global | 全部流量强制走代理 | P0 |
| NET-04 | 192.168.34.x | ap-34x | **默认**走静态住宅 IP；**白名单**（如远程桌面相关域名/端口/IP）走直连 | P0 |
| NET-05 | 192.168.35.x ~ 255.x | 待扩展 | 链式代理/其他住宅 IP；命名与规则模式对齐 v6 住宅方案 | P2 |

### 3.1.1 住宅网段白名单（v6）

| 需求编号 | 描述 | 优先级 |
|---------|------|--------|
| RES-01 | 源为住宅网段（如 34.x）时：命中白名单的目的流量 **DIRECT**，其余仍走该网段住宅出口 | P0 |
| RES-02 | 动机：远程连接经住宅代理会导致延迟过高；仅对白名单「借道」国内直连出口 | P0 |
| RES-03 | 白名单：`DIRECT-34-relays.yaml`（端口/IP）+ `DIRECT-34.yaml`（域名），由 `configs/v8.yaml` 中 `SUB-RULE` + 两条 `RULE-SET` 引用 | P0 |

### 3.3 多机场管理

| 需求编号 | 描述 | 优先级 |
|---------|------|--------|
| AIR-01 | 支持 5 个机场订阅，按梯队分组，自动拉取更新 | P0 |
| AIR-02 | 三梯队分层：C 主力（2机场）> B 保底（2机场）> A 优质（1机场） | P0 |
| AIR-03 | 视频/社交类走 C→B→A（主力先上，省流量优先） | P0 |
| AIR-04 | AI/重要业务走 A→C→B（优质先上，稳定优先） | P0 |
| AIR-05 | 某机场或同国全部梯队掉线时自动故障转移；同国全部失效后由主要国家顶层组内展开的跨国叶子组继续兜底 | P0 |
| AIR-06 | 按地区筛选节点（港/日/新/美/台/英/德/法/韩/马/荷/越） | P0 |
| AIR-07 | 自动过滤机场展示/说明/流量提示等无用节点 | P1 |
| AIR-08 | 跨国兜底不含香港；直接在各主要国家顶层组中展开底层地区叶子组，不新增 `fallback → fallback` 层级，也不允许顶层地区组互引 | P0 |

### 3.4 策略组 UX 需求

| 需求编号 | 描述 | 优先级 |
|---------|------|--------|
| UX-01 | 策略组名称必须标注所属网段（如 `Claude 32.x`） | P0 |
| UX-02 | 应用策略组只显示国家/地区名，不显示机场/故转/全部节点 | P0 |
| UX-03 | 面板排列顺序：出口组 → 应用组 → 地区组 → 机场子组 | P0 |
| UX-04 | AI 大类拆分为独立平台（不要笼统的"AI 平台"） | P0 |
| UX-05 | 所有故转合并为一个统一的故障转移组 | P1 |

### 3.5 DNS 安全

| 需求编号 | 描述 | 优先级 |
|---------|------|--------|
| DNS-01 | 使用 fake-ip 模式防止 DNS 泄漏 | P0 |
| DNS-02 | 国内域名走国内 DOH（阿里/腾讯），海外域名走 8.8.8.8/1.1.1.1 | P0 |
| DNS-03 | 代理节点域名解析不经过代理（防鸡蛋问题） | P0 |

### 3.6 OpenClash 普通代理入口

| 需求编号 | 描述 | 优先级 |
|---------|------|--------|
| PROXY-01 | 普通入口使用 HTTP `7890`、SOCKS5 `7891`、HTTP/SOCKS5 混合 `7893`；无 crawler 专用 listener | P0 |
| PROXY-02 | 账号密码在 OpenClash 的 SOCKS5/HTTP(S) 认证页面统一管理，公共模板不含真实凭据 | P0 |
| PROXY-03 | 规则模式下普通入口进入主 `rules`，沿用源网段分流：31.x 直连、32.x 按平台、33.x 全局代理、34.x 白名单直连/其余住宅 | P0 |
| PROXY-04 | 需要按平台分流的程序部署在 32.x，并由 Mihomo 实际识别为 32.x 来源，复用既有平台策略组 | P0 |
| PROXY-05 | 不再维护 31 个 HTTP 专用策略组、`http-rules` 子链及 9 个 HTTP 专用 rule-provider；保留主规则与 `residential34` | P0 |
| PROXY-06 | 入口不绑定机场；机场流量归属由最终选中的节点决定，直连不消耗机场代理流量 | P0 |
| PROXY-07 | 可在 Zashboard 连接详情核对来源 IP、匹配规则、代理链和最终节点；故障切换后重新确认机场归属 | P1 |
| PROXY-08 | OpenClash 覆写模板后，部署者须核验实际运行端口、认证和规则模式；入口连通与目标平台可用分别验证 | P0 |

| CLIENT-03 | 不包含住宅代理、路由器专用入口和源网段分流；仅监听本机 | P0 |
| CLIENT-04 | 代理、控制器和 DNS 仅监听本机，不向局域网共享 | P0 |

### 3.8 设计决策记录

| 决策编号 | 决策 | 理由 | 影响范围 |
|---------|------|------|---------|
| DEC-01 | 程序复用 OpenClash 普通入口和主 `rules` | 统一端口、认证与策略操作，移除独立 crawler 配置 | 路由器 v8 |
| DEC-02 | 32.x 的程序直接使用已有平台策略组 | 面板调整平台地区后，新连接按该组当前选择与健康状态出站 | PROXY-04 |
| DEC-03 | 按最终节点确认流量归属 | 端口、地区组和梯队只参与路由选择；故障切换可能改用另一机场 | PROXY-06 |
| DEC-04 | 在连接详情核验实际 sourceIP | 容器、中继或 NAT 可能改变内核看到的来源，不能仅凭程序部署位置判断网段 | PROXY-07 |
| DEC-05 | 不以目标站点 HTTP 200 作为代理配置的唯一验收依据 | 入口可用不保证目标站点允许访问；站点授权、限流与客户端行为需单独排查 | PROXY-08 |

v7 的独立 HTTP 池设计属于历史方案，当前 v8 不再采用。

## 4. 非功能需求

| 需求编号 | 描述 | 优先级 |
|---------|------|--------|
| NFR-01 | 配置文件可扩展：新增平台/网段只需添加几行 | P1 |
| NFR-02 | 规则集优先使用 .mrs 二进制格式（加载快、体积小） | P1 |
| NFR-03 | 敏感信息（订阅 URL/住宅 IP 凭据）集中在文件顶部，便于管理 | P1 |
| NFR-04 | 控制面板 (zashboard) 可远程管理策略 | P2 |
| NFR-05 | 本仓 rulesets：**文件名** = `策略简写-网段`（住宅白名单可拆 `DIRECT-34-relays.yaml` + `DIRECT-34.yaml`）；**provider 键** = 小写+下划线（如 `direct_34_relays`、`direct_34`） | P0 |

## 5. 约束条件

- 运行平台：OpenWrt + Mihomo 插件
- 内核版本：Mihomo (Clash Meta) 最新稳定版
- 硬件限制：路由器内存有限，规则集不宜过多
- 网络环境：中国大陆，部分域名/IP 被墙
- gstatic 健康检查必须使用 `expected-status: 204`；跨国与地区 fallback 周期为 60 秒

## 6. 验收标准

以下是部署后的验收要求；本次文档更新不表示已完成真实路由器测试。

1. 规则模式下，31.x 请求直连；32.x 请求按现有平台规则分流；33.x 请求进入全局策略组。
2. 34.x 请求命中 `direct_34_relays` / `direct_34` 时直连，其余进入住宅出口；主规则与 `residential34` 保持原行为。
3. HTTP `7890`、SOCKS5 `7891`、混合 `7893` 分别使用正确协议连接成功，无重复监听或端口占用错误。
4. OpenClash 启用认证后，有效账号能够连接，错误账号与未提供认证的请求被拒绝；以实际加载配置为准。
5. 32.x 的程序通过普通入口访问已配置的平台，Zashboard 显示来源为 32.x、命中对应平台规则，并使用面板当前选择的策略链。
6. 分别从 31.x、33.x、34.x 使用普通入口验证来源规则，不假定代理账号决定网段或出口；34.x 需同时测试白名单与非白名单目标。
7. 连接详情可追踪到最终节点及机场 provider；若最终为 DIRECT，则不计入机场代理流量。健康状态变化或重新选择策略后，以新连接为准。
8. 当前路由器模板没有 crawler 账号、HTTP 专用策略组或 `http-rules`；保留 62 个策略组、42 个 rule-provider、5 个机场 provider，地区部分为 19 组。
9. 规则集能下载并被内核正确加载，面板与日志无相关错误；HTTP 200 本身不足以证明规则内容正确。
10. 地区与平台组排列符合面板布局；AI 默认选择稳定梯队，视频默认选择省流梯队。
11. 单机场掉线后能自动故障转移；主要国家同国梯队全失效后，按配置的公共跨国叶子顺序选择健康出口，不包含香港；首选恢复后可重新优先使用。
12. 所有 gstatic 健康检查仅在状态 204 时判定可用；地区 fallback 配置周期为 60 秒。健康检查成功不替代目标平台实测。
13. 配置不使用 `global-client-fingerprint`，5 个 proxy-provider 通过 `override.client-fingerprint: chrome` 设置代理节点指纹；部署时用实际内核检查兼容性。
14. 公共模板与文档示例不包含真实订阅、认证或住宅代理凭据。OpenClash 保存/应用后重新确认实际运行配置、规则模式与 sourceIP。
